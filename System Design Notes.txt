MESSAGE QUEUES 

Delivery model : 
| ----------------------- | ----------------------------------------------------------- | ------------------------------------ | -------------------------- |
| Point-to-Point (P2P)    | One producer → one consumer; message deleted after consumed | Task queues, job processing          | SQS, RabbitMQ              |
| Pub/Sub                 | One producer → many subscribers via topics                  | Notifications, event broadcasting    | Kafka, SNS, Google Pub/Sub |
| FIFO Queue              | Messages processed strictly in order received               | Payment processing, order sequencing | SQS FIFO, RabbitMQ         |
| Priority Queue          | Higher-priority messages jump the queue                     | Incident alerts, SLA-sensitive tasks | RabbitMQ                   |
| Dead Letter Queue (DLQ) | Holds messages that failed processing repeatedly            | Error handling, debugging            | SQS DLQ, Kafka             |
| Delay Queue             | Messages hidden for a delay before becoming visible         | Scheduled retries, deferred tasks    | SQS Delay                  |

By Push vs Pull


| Model | Description                                 | Best For                                 |
| ----- | ------------------------------------------- | ---------------------------------------- |
| Push  | Broker actively sends messages to consumers | Real-time fanout, low-latency delivery   |
| Pull  | Consumers poll the broker for messages      | Rate-controlled processing, backpressure |

| Tool              | Model         | Best For                                              |

CDN (Content Delivery Network)
| Feature                  | Push CDN                                     | Pull CDN                                                    |
| ------------------------ | -------------------------------------------- | ----------------------------------------------------------- |
| How content gets to edge | You manually upload to CDN PoPs              | CDN fetches from origin on first request karanpratapsingh​  |
| First request latency    | Low (already cached)                         | High (cache miss, goes to origin) systemoverflow​           |
| Subsequent latency       | Low                                          | Low (10–25ms from edge) systemoverflow​                     |
| Operational overhead     | High (you manage uploads/expiry)             | Low (CDN manages automatically) dev​                        |
| Best for                 | Static sites, software binaries, live events | Frequently changing content, large catalogs systemoverflow​ |
| Example                  | Pre-loading a game update                    | Netflix long-tail video catalog                             |
Most modern websites use Pull CDNs because they are easier to manage and update. Hybrid strategies (push popular content, pull long-tail) dominate at scale.
